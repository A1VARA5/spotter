### F3. Channel3 search credits can be spent without limit (Medium)

**Where:** `src/core/watch.ts:220-233` (`startWatch`: cap check, then `c3.search`, then the early return for an existing watch), reached from `src/server/agent.ts:120-134` (MCP `watch_price` with `item`), `src/app/api/mcp/route.ts:81-98` and `src/app/api/watches/route.ts:20-31`.

**Problem:** the caps (`CAP_WHERE`) count active watches and watches created per day. A Channel3 `/search` call costs 1 credit ($0.007 after the free 1,000 a month, `docs/channel3/pricing.md`), and it runs before any row exists. A call that ends without a new watch never counts toward a cap:
- the item isn't found (404) or Channel3 can't track it,
- the product is already watched by this family (`existing` returns early, line 233),
- the insert loses the race and `release` runs.

So a family under its 5 active watches can call it again and again, and each call is one search.

**Exploit scenario:** anyone can start a demo family for free, create an agent key and point a script at `/api/mcp`. It then calls `watch_price` with made up item names, or with the same item over and over. Each call spends one Channel3 search and nothing stops it. `POST /api/watches` with one watchable payment id does the same with only the household cookie. 10,000 calls would cost about $70 and would also use up the hackathon promo credits that the live demo needs.

**Proof:** `F3 ... stops spending searches on a family that keeps asking for products Channel3 can't find` (25 calls, 25 searches) and `... doesn't spend a search again for a product the family is already watching` (5 calls, 5 searches, 1 watch).

**Fix:** take a slot before searching, the same way `src/watchtower/price.ts` does with `price_checks` (per family per day plus overall per day, in one statement), and count failed and duplicate attempts too. Cache `search` results by `currency:item` the way `makeMarket` does with `market_cache`, so asking for the same item again costs nothing. Also look up an existing watch by normalised item before searching. Related, but older than this diff: the MCP `find_products` tool (`src/app/api/mcp/route.ts:56-68`) also calls `searchProducts` with no cap. Put it behind the same slot.

### F1. Peek checks only the first hop, so a link can redirect inside KERNEL's network (Medium)

**Where:** `src/server/peek.ts:155-168` (`pageFor`), `src/server/peek.ts:199-206` (`browsers.create({ start_url })`).

**Problem:** `pageFor` checks that `case_file.page.url` came from the payment's own message and that its host resolves to a public address. Then KERNEL's browser opens it and follows whatever happens next: HTTP redirects, meta refresh, JS navigation, and DNS rebinding (already noted in `docs/kernel-notes.md`). The case file even records where the link really went (`case_file.page.finalUrl`), but the peek never looks at it. `stealth: false` means no KERNEL proxy, so the browser goes out from KERNEL's own network. The relayed screenshots, plus scrolling, let the viewer read what that page shows.

**Exploit scenario:** someone in a demo family sends themselves a payment request (Try page or their own agent key) whose message links to a public host they control. That host redirects to a cloud metadata address or another internal address. The peek opens it in KERNEL's browser and streams pictures of the result to them, three times a day per family. Spotter becomes a screenshot relay into whatever KERNEL's browser network can reach. The same is true of the case agent's KERNEL visit, which predates this diff and stores a screenshot. The peek adds 90 s of live looking and scrolling. Whether KERNEL's browsers can actually reach anything sensitive is **unproven**; that's on KERNEL's side.

**Proof:** `F1 ... does not open a KERNEL browser on a link whose recorded final address is link local`: the case file's `finalUrl` is `http://169.254.169.254/...` and the peek still calls `browsers.create` and answers 200.

**Fix:**
1. In `pageFor`, also refuse when `case_file.page.finalUrl` is present and its host isn't public (`safeToFetch`), or when it isn't http or https.
2. Resolve the redirect chain again at peek time with the guarded resolver in `links.ts` (`guardedFetch`, manual redirects, every hop checked), and pass the checked final URL as `start_url`.
3. During the peek, refuse a frame if the browser has moved to a private host, if KERNEL exposes the current URL.
4. Ask KERNEL whether their browsers' egress is isolated from internal and metadata ranges, or route peeks through an egress proxy that blocks private ranges. Steps 1 and 2 can't stop JS navigation or rebinding after start, so step 4 is the real fix.

### F2. Failed peek starts don't count, so KERNEL browsers can be created without limit (Medium)

**Where:** `src/server/peek.ts:185-186` (`close_reason is distinct from 'failed'` in both cap counts), `src/server/peek.ts:228-236` (the `finally` that marks a start `failed`).

**Problem:** a start that times out after `CREATE_MS` (12 s), or that fails after the browser was created, is closed as `failed` and drops out of both daily caps. A create that timed out can still produce a billed browser (it is deleted when it arrives, or ends at the 20 s backstop, or orphans if it arrives after the SDK's 27 s limit). The one open peek rule makes starts serial within one family, but every demo family can loop.

**Exploit scenario:** someone makes `browsers.create` slow or failing for their own link and loops start requests across many demo families. None of them ever reaches the 3 per family or 30 overall caps, and each attempt can bill a headful browser for up to about 30 s. The trigger is **unproven**: it needs KERNEL's `create` to wait on `start_url` loading (a page that hangs), or a KERNEL error that can be provoked. The counting gap itself is proven.

**Proof:** `F2 ... never asks KERNEL for more browsers than the household's daily cap, even when every start times out`: 6 starts with a create that never answers, 6 `create` calls (cap 3).

**Fix:** count every attempt that reached `browsers.create`. Keep a separate `close_reason`, but count `failed` rows that got as far as calling KERNEL. Mark them, for example with a `create_called_at` column set just before `create`, and count rows with that column set. If needed, give failures their own looser cap (for example 6 a day per family). Then a KERNEL outage doesn't lock families out but still has a ceiling.

### F4. The Channel3 webhook accepts unsigned deliveries when the secret is unset (Low)

**Where:** `src/market/webhook.ts:32-37`, `src/app/api/channel3/webhook/route.ts:10`.

**Problem:** with `CHANNEL3_WEBHOOK_SECRET` unset, any POST is accepted and logged as a warning. The design limits the damage: only the product id is used, offers are read again from Channel3, and the 10 minute quiet window plus the 5 watch batch apply. But it fails open. Every forged delivery still costs a `/v1/products` read (free) and a `/v0/price-tracking/history` read for up to 5 watches, and it triggers drop notices sooner than the daily job would.

**Exploit scenario:** someone who learns or guesses a watched product id (ids are short, like `VpRxZ86`) can make Spotter check those watches every 10 minutes. A forged delivery can't fake a price drop. The issue is that "unset" quietly means "open", which is easy to miss in production.

**Proof:** `F4 ... refuses deliveries when CHANNEL3_WEBHOOK_SECRET is unset`: the hint runs for an unsigned body.

**Fix:** fail closed. With no secret, answer 503 ("not configured") and log once, the way `handleReconcile` treats a missing `CRON_SECRET`. The daily job still finds drops, so nothing is lost. The Svix check itself is correct: raw body, `id.timestamp.body`, base64 HMAC with the decoded `whsec_` key, 5 minute window, any of several `v1,` signatures, `timingSafeEqual` on equal length buffers. A replay inside the 5 minutes isn't rejected by `svix-id`, but the quiet window and the conditional `dropped` update make it harmless. Storing `svix-id` for 10 minutes would be an optional extra.

### F5. Discord drop notice puts the item into markdown without escaping it (Low)

**Where:** `src/server/watch-notify.ts:43` (`**${lines[0]}**`). `lines[0]` contains `w.item`, which is the agent's or payment's own wording (`watch_price` `item`, or `payments.request.item`), and `best.shop`.

**Problem:** Telegram (`tgEsc`) and email (`esc`) escape the text, but Discord doesn't. Bot messages render masked links (`[text](url)`), bold and headings. An item name can show up in the spotter's DM as a link that looks like Spotter's own.

**Exploit scenario:** an agent that was prompt injected passes an item with a masked link. If the watch is created and drops, the spotter's DM from Spotter shows link text the attacker picked, pointing anywhere. It's hard to reach today: `bestProduct` → `sameProduct` needs every word of the item, except one, to be in a real Channel3 title. So the link text and the URL's words must mostly appear in the product's title. That makes it hardening, not an open hole.

**Proof:** `F5 ... doesn't let an item name become a masked link in the spotter's Discord DM`: `makeDropNotify` sends the item's `[..](https://..)` unchanged.

**Fix:** escape Discord markdown in untrusted pieces (`\`, `*`, `_`, `~`, `` ` ``, `|`, `>`, `#`, `-`, `[`, `]`, `(`, `)`) before building the message, or keep only letters, digits, spaces and basic punctuation in `item`. Send with `allowed_mentions: { parse: [] }` too. Use the Channel3 `title` (live data, not agent text) in the notice instead of the agent's `item`.

### F6. Private address guard misses IPv6 forms that embed an IPv4 address (Low)

**Where:** `src/agents/links.ts:431-456` (`safeToFetch` and `PRIVATE`). The function is older than this diff, but now it's the peek's only network guard (`src/server/peek.ts:167`).

**Problem:** `[::ffff:169.254.169.254]` is refused correctly. The NAT64 form `64:ff9b::a9fe:a9fe` and the 6to4 form `2002:a9fe:a9fe::`, which both embed `169.254.169.254`, are treated as public.

**Exploit scenario:** a message links to `http://[64:ff9b::a9fe:a9fe]/`. On a network with a NAT64 gateway that translates it, the browser reaches the IPv4 metadata address. Whether KERNEL's network (or Vercel's, for the case agent's own fetches) has such a gateway is **unproven**. Most NAT64 gateways refuse link local targets.

**Proof:** `F6 ... treats NAT64 and 6to4 forms of the cloud metadata address as private`.

**Fix:** add `64:ff9b::/96`, `64:ff9b:1::/48` and `2002::/16` to the blocked list. Or pull out the embedded IPv4 address and run it through the IPv4 check.

## Reviewed, no finding (Info)

- **I1. Peek authz:** start, frame, scroll, close and DELETE all take the household from the signed `spotter_hh` cookie, and every query is scoped by `household_id` (`getPayment(db, id, householdId)`, `livePeek`, `closePeek`). Another household gets 404 or 410, and KERNEL is never called (an existing test in `peek.test.ts` covers this). The cookie is `SameSite=Lax`, so a cross site POST (start, scroll, close) or `<img>` frame request doesn't carry it. The URL always comes from the case file, never from the request body.
- **I2. KERNEL ids and live view:** start answers only `{ secondsLeft, view }`. The session id is sealed with AES-256-GCM under purpose `kernel-peek` before storage, and no live view URL is requested or stored. Logs go through `msg()`, which blanks 16+ character tokens that contain a digit. That relies on KERNEL session ids matching that shape, which isn't checked. A short or all letter id would be logged as is. Low risk, since an id is useless without the API key. Could log a hash of the id instead.
- **I3. Frames after close:** `livePeek` requires `closed_at is null and ends_at > now()`. One frame already past that check when close runs can still return a single picture before the browser is deleted. That's harmless. The 400 ms per frame slot is a conditional update, so concurrent frames can't get round it.
- **I4. PNG check:** content type `image/png`, the 4 byte signature, a size cap, then served with `nosniff` and shown through a blob URL in `<img>`. Even a non PNG couldn't run script there. Small hardening: check the full 8 byte signature, and cap the body while streaming instead of after `arrayBuffer()` when `content-length` is missing (KERNEL is trusted, so this is robustness).
- **I5. Caps under concurrency:** one open peek per household holds under races (partial unique index). The overall 30 a day can overshoot slightly under READ COMMITTED, as `docs/kernel-notes.md` notes. Demo families can use up the overall caps, peek 30 and watches 40 a day, and lock everyone else out for the day. That's an accepted availability trade off, documented.
- **I6. Gran view agent:** payee names and Spotter's reasons reach the model as tool data labelled "data, not instructions", and the role forbids suggesting approval. The agent has one read only tool (`my_month`, no ids) and can't act. Answers are drawn as React text after markdown stripping. No `dangerouslySetInnerHTML` or AG Grid HTML renderers in the new widgets, so no XSS path. What's left is prompt only and **unproven**: a payee name like "call this number to unlock" could be repeated to Gran, and nothing checks the output. The Gran role and tool list are also put together in the browser (Studio.tsx), so they limit Gran's own session, not a hostile client. That's fine, because the client is the family itself. Suggested hardening: cap payee names in `granForAgent` (for example 40 characters), and drop or replace an answer that has a phone number, URL or "approve/pay/send/try again" outside the fixed `ADVICE` text.
- **I7. Watch authz:** `stopWatch` and `listWatches` are scoped to the household. `watchFromPayment` checks the payment's household and, for agents, `onlySpender`. MCP `watch_price` resolves the agent from the verified bearer token. Drop notices go only to the spotter's channels. Telegram button URLs are https only and come from Channel3. Email escapes every piece.
- **I8. PayPal `PAYMENT.CAPTURE.DECLINED`:** same rule and same "different capture id" guard as `DENIED`. It runs only after PayPal's verify API (unchanged) and `paypal_events` dedupe. It never moves money. No issue.

## Suggested order

F3 first (proven, anyone can reach it through a demo family, real money). Then F1 steps 1 and 2 and the KERNEL egress question, then F2, then F4, F6 and F5 together as one small hardening commit.
